# 六阶段治理工作流细则

> 阶段与门禁表是 `docs/agent-governance.md` §五（唯一出处），本文件不再复制；这里只保留技能执行所需的问题模板、总结模板、渐进落地步骤与脚本输出契约。

## 一、阶段顺序（细节见标准 §五）

一 系统审计 → 二 问题清单 → 三 方案 → 四 实施 → 五 验证 → 六 治理总结。逐级通过门禁；证据不足的条目记入「待验证」，不跳步。

## 二、问题条目模板

```md
### <问题标题>

- **问题描述**：
- **证据 / 复现条件**：（仓库相对路径 + 符号名；不写行号）
- **根因或最可信假设**：（标注「已确认」或「假设」）
- **影响范围**：
- **现有守卫及其有效性**：
- **推荐修复方向**：（根因修复 / 契约修复 / 复用机制 / 新增守卫）
- **预期收益**：
- **回归风险**：
- **验证方式**：（测试文件与用例名、命令、运行态探针）
```

## 三、治理总结模板

```md
### 治理总结
- 改了什么：
- 为什么改：
- 修复的根因：
- 新增守卫及必要性（7 问摘要）：
- 删除/合并/替换的守卫及依据：
- 未解决的历史问题：
- 实际执行的测试与真实结果（含退出码；未执行项单列）：
- 剩余风险与后续建议：
```

## 四、渐进落地步骤

1. **建立基线**：先读项目结构、提示词、规则文件、工具接口、测试与异常处理，不修改代码。
2. **识别重复与失效机制**：按五类守卫分类，找出职责重复、缺少证据、掩盖根因的机制。
3. **从一个高价值问题开始**：选择有明确复现条件、影响范围清晰的问题，比较根因修复与局部补丁。
4. **建立回归测试**：先证明修复原问题，再证明相关行为与安全边界未退化；失败时继续定位原因，不叠加守卫。
5. **逐步清理历史包袱**：在有测试和证据的前提下合并重复逻辑、替换脆弱机制、删除失效分支。
6. **融入日常迭代**：每次功能开发、模型升级、工具扩展与架构变更后，做一次轻量守卫审查，防止复杂度回涨。

## 五、脚本输出契约（`scripts/governance-audit.workflow.mjs`）

输入：`args.scope`（必填，模块或目录范围）、`args.focus`（可选，审计焦点数组）、`args.maxFindings`（可选）。

三种返回形状：

1. **全部成功**：`{ ok: true, partial: false, scope, focus, audits, failedLines: [], issues, proposals, readOnly: true, requiresHumanApproval: true, next }`。
2. **部分失败**：`{ ok: true, partial: true, ...同成功字段, failedLines: [失败焦点], issues, proposals }`——消费方必须看 `partial`，不能把缺线当成没问题。
3. **全部失败 / 汇总失败 / 方案失败**：`{ ok: false, error, failedLines, ...已产出的字段, readOnly: true, requiresHumanApproval: false }`——不产出方案比较，先修运行环境。

边界：脚本不写文件、不执行生产操作；审计子 agent 的「只读」是提示词约束，不是权限隔离。
