# 守卫分类与处理策略

> 本文件是 `governance-architecture` 的参考材料：先分类，再决定「保留、合并、替换、删除、暂缓」。

## 一、五类守卫

### 第一类：不可缺少的安全边界

典型：身份认证与授权、资源访问控制、沙箱隔离、高风险操作授权、敏感数据保护、数据完整性约束、外部副作用的执行限制。

处理策略：**保留安全保证**，允许用更可靠的实现替换，但必须验证替代机制提供等价或更强的保证。不得因为「看起来多余」删除。

### 第二类：业务不变量

典型：状态转换合法性、金额或数量与资源配额约束、数据引用完整性、事务一致性、工具输入输出契约。

处理策略：尽可能收敛到数据模型、领域层、事务层或权威执行层统一实现；避免同一规则在多个位置独立演化。

### 第三类：必要的运行可靠性机制

典型：有界重试、超时控制、幂等性保护、熔断与资源限制、故障恢复、外部依赖降级。

处理策略：明确触发条件、重试上限、预算、幂等性、终止条件与观测指标；避免无限重试、无边界降级和隐藏失败。

### 第四类：模型行为约束

典型：模型输出格式验证、工具参数语义检查、不可信上下文隔离、规划结果验证、生成结果的业务规则检查。

处理策略：只对模型确实无法稳定保证的部分设置必要约束；关键副作用必须在可信执行边界再次做权威授权与验证。**提示词不是权限控制。**

### 第五类：历史遗留与重复守卫

典型：针对已修复旧故障保留的分支、多模块重复检查同一条件、无清晰责任归属的全局拦截器、永不触发的 fallback、仅掩盖底层缺陷的异常捕获、已被新接口/类型/权限机制取代的逻辑。

处理策略：先审计与验证，满足删除条件后再清理；名称、注释或历史提交的「无用」声明不能作为唯一证据。

## 二、不同信任边界可以保留独立重复检查

入口校验与数据库约束即使检查相似条件，也可能有不同的责任与失效模型；不得未经分析就合并。合并的前提是证明一种机制能覆盖另一方的失效模式。

## 三、删除与合并的准入条件

1. **等价或更强的替代机制**已存在，并有测试或运行证据。
2. **真实调用与触发证据**：调用点、指标、测试或 issue 记录；不存在命名或注释之外的证据时不得删除。
3. **责任回到不变量本身**：由类型、状态机、事务、数据库约束或权限边界承担。
4. **先补回归证据再删**：删除前修复能抓回原故障的测试，删除后测试仍绿。
5. **证据不足则暂缓**：保持安全拒绝行为，把待验证项记录到 roadmap、ADR 或 issue。

## 四、反模式

- 为「代码整洁」删除安全机制。
- 用命名、注释或历史提交断言某项已无用。
- 同一不变量在多个模块独立演化、长期并存。
- 永不触发的 fallback、只掩盖底层缺陷的 catch、无终止条件的重试。
