# 架构治理主规范

## 定位

本技能是治理套件的**原则与路由入口**：它决定问题该在哪一层解决、要不要加守卫、何时删守卫。它不替代项目事实（`AGENTS.md`）与历史决策（`docs/adr/`），也不重复其它治理技能的执行步骤；技能格式与路由标准见 `docs/agent-governance.md`。

## 判据

1. 守卫不是越多越好，而是越少、越明确、越可靠。
2. 架构约束优先于局部防御性补丁；根因修复优先于症状拦截。
3. 明确的不变量优先于散落在多个模块里的重复检查。
4. 最小权限与执行隔离优先于依赖模型自觉；提示词不是权限控制。
5. 可验证的正确性优先于「感觉更安全」。
6. 新增机制必须证明必要性；删除机制必须证明不破坏重要保证。
7. 代码行数、守卫数量、抽象数量少，不等于质量高；简单方案不得削弱必要的安全边界。
8. 每次进化都要复审历史设计，不默认旧规则永久有效。

**分析顺序（不得跳步）**：

1. 定位实际失败行为：证据、调用链、输入输出、复现条件；区分直接原因、根因与相关因素。
2. 检查架构与契约：接口是否含糊、是否允许非法状态、是否多处重复同一约束、是否在错误层次处理。
3. 选择最小可靠修复：修根因 → 强化契约 → 消除非法状态 → 约束移到正确责任层 → 复用既有机制 → 最后才新增守卫。
4. 验证：原问题解决、正常场景与边界不回退、权限与安全保证仍在、未引入重复逻辑与新隐式依赖。

**架构优化优先级**（自上而下）：边界与职责 → 接口契约 → 类型与数据模型 → 状态约束 → 最小权限与资源控制 → 权威执行层验证 → 必要运行时守卫 → 监控告警恢复 → 单案例局部补丁。不同信任边界可以保留独立重复检查（如入口校验与数据库约束），不得未经分析就合并。

**守卫分类**见 `references/guard-classification.md`；AI Agent 系统专项检查见 `references/agent-system-checklist.md`。历史机制必须给出结论之一：保留、合并、替换、删除、暂缓。

## 流程

1. 判定任务类型：架构审计、修改前决策、修改后审查、台账维护、工作流编排，加载对应技能，不在本技能里展开步骤。
2. 用「分析顺序」前两步确认事实与契约，再进入方案选择。
3. 对每个候选方案回答：保护什么、根因还是症状、是否有更稳定的架构方案、能否复用或合并既有机制、新增哪些状态/分支/依赖、如何验证、将来是否会成为历史包袱。
4. 方案涉及新增或删除守卫时，加载 `governance-change-guard` 走 7 问与删除证据。
5. 修改完成后加载 `governance-review` 做独立审查。

## 输出与验收

- 结论必须区分：已确认事实、待验证假设、纯优化建议。
- 每个被修改或被保留的守卫都要有「保护目标 + 验证方式」；无法给出证据时标注「待验证」，不得冒充根因。
- 验收以可执行证据为准：测试退出码、静态检查、类型检查、运行态探针；未执行的检查必须明确标注。

## 禁止

- 遇到每个错误就加一层 `if`、`try/catch`、validator 或 fallback。
- 吞异常、返回默认值、静默降级掩盖故障；无限重试掩盖不稳定。
- 把模型提示词、自我检查或再次生成的答案当作独立安全边界。
- 未验证就宣称根因；为体现优化成果强行制造修改或删除。
