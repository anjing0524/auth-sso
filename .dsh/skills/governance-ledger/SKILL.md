# 守卫台账标准

## 定位

台账回答一个问题：**这条守卫为什么存在、由谁验证、什么时候可以退役**。它是决策记录，不是管理守卫的复杂系统：小型项目用 Markdown 表格即可，只有守卫数量、风险与协作规模确实需要时才自动化。

## 判据

- **条目格式**（字段、条目模板、生命周期判定表）唯一出处：`references/guard-ledger-template.md`。
- **政策与落位**（台账放在哪、删除证据要求、为什么不建全局清单）：`docs/agent-governance.md` §六。
- 本技能只做三件事：登记条目、给出生命周期结论、记录复审条件；不新造字段、不建第二套清单。
- 新增守卫先回答 `governance-change-guard` 的 7 问；删除或合并必须证明替代机制等价或更强、有回归证据；证据不足 → 暂缓并保持 fail-close。

## 流程

1. 确定审查范围（模块、信任边界或一类守卫），列出现有守卫及其权威位置。
2. 按五类分类（安全边界、业务不变量、运行可靠性、模型行为、历史遗留与重复）逐条登记。
3. 按模板填写字段并标注证据来源；生命周期结论只允许保留、合并、替换、删除、暂缓。
4. 删除或合并项附替代机制与回归证据；未解决项写清暂缓原因与复审条件。
5. 需要长期保留的结论沉淀到 ADR 或 `docs/roadmap.md`。

## 输出与验收

- 台账条目（模板见 references）与生命周期结论。
- 删除或合并项的证据与测试结果。
- 未解决项与暂缓原因，不得静默消失。

## 禁止

- 为了「整洁」删除安全机制；用命名、注释或历史提交作为无用证据。
- 建立需要单独维护、与实际守卫脱节的全局清单系统。
- 把台账当成交付表演：条目没有证据、没有所有者、没有复审条件。
