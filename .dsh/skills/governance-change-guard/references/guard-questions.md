# 守卫问题清单（新增 7 问 / 删除 5 证）

## 一、新增守卫：必须逐条回答

| # | 问题 | 合格证据 |
|---|---|---|
| A | 它保护什么？ | 具体的不变量、资源、权限、业务规则或故障边界 |
| B | 它防止什么？ | 具体失败场景 + 可复现输入、调用路径或测试 |
| C | 为什么必须放在这里？ | 说明为何类型、契约、权限或已有机制更不可靠 |
| D | 责任边界是什么？ | 输入、输出、副作用、错误处理方式、与其他机制的关系 |
| E | 如何证明有效？ | 测试、静态约束、权限验证或运行指标 |
| F | 是否与已有机制重复？ | 列出相似守卫、校验、异常处理、重试、降级与兼容代码 |
| G | 退出条件是什么？ | 什么情况下删除、替换、合并或简化 |

回答不了 A–G：先补证据或改提架构方案，不得凭习惯或主观安全感新增守卫。

## 二、删除或合并守卫：必须给出

1. **替代机制**：删除后由谁承担同一责任（类型、状态机、事务、权限边界、数据库约束）。
2. **等价或更强**：证明替代机制覆盖原守卫的失效模式；不同信任边界的重复检查不得随意合并。
3. **调用或触发证据**：调用点、指标、测试或 issue 记录；命名、注释、历史提交不能作为唯一证据。
4. **回归证据**：删除前先有能抓回原故障的测试，删除后测试仍绿。
5. **复审条件**：架构、依赖、权限或业务变化时重新检查。

## 三、fail-close 规则

证据不足时保持安全的拒绝行为，同时把「待验证项」记录到 `docs/roadmap.md`、ADR 或 issue；不得为了减少守卫或让测试变绿而默认放行。安全边界、数据完整性与权限约束三类不得仅因「看起来多余」删除。
