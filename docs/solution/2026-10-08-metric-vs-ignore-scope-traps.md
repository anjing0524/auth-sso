# 度量与忽略范围 —— 两个把自己骗过去的陷阱

> 沉淀自 ADR-019（Controller 行数约束）与 ADR-020（审计持久性）的修订过程。
> 这两个陷阱的共同特征：**工具给出的绿色信号是有条件的，而条件被悄悄放宽了。**

## 陷阱一：用错误的度量优化，会得到"改了很多、目标没动"的结果

### 现象

架构评审认为 "Controller 函数 ≤20 行" 被普遍违反（22 个里 19 个超标）。连续两轮抽取
重复模式（写后缓存失效原语、安全写编排 `withScopedRow`/`withScopedWrite`）之后，
超标数量**从 18 增到 19**——重复度明显下降，行数却上升。

当时的困惑被如实记录为"根因诊断不完整"。真正的原因是：

> **行数不是复杂度的代理。每引入一个编排原语，都在函数体里增加行数。**

### 证据

用 TypeScript 编译器 API 只读解析 22 个 Server Action：

| 指标 | 实测 |
|---|---|
| 整段 action 的**圈复杂度** | 最大 **8**，0 个 > 10 |
| 最大嵌套深度 | 3 |
| 超 20 逻辑行的 14 个中 | **12 个圈复杂度 ≤ 5** |
| 声明式守卫 spec（`withScopedWrite` 的 options） | **18% 逻辑行** |

长度来自**声明式配置与多行参数**，不是逻辑。度量与目标正交，所以无论怎么改都不同步。

### 最佳实践

1. **优化一个指标前，先证明它与目标相关。** 拿真实代码量一次，而不是接受一个
   看起来合理的数字。本例中"20 行"听起来合理，实测却与复杂度几乎无关。
2. **声明式配置会污染行数度量，且没有工具能排除它。** ESLint 的
   `skipBlankLines` / `skipComments` 只跳过空行与纯注释行，**跳过不了 options 对象**。
   当一个函数的主要长度来自配置块时，行数度量已经失去意义。
3. **权威来源普遍反对硬性行数上限**：Google C++ Style Guide「no hard limit」、
   Ousterhout「arbitrary numerical limits … exacerbates」、Fowler「size isn't
   important」、Hatton 1997 缺陷密度呈 U 形（中等组件最可靠）。工具默认值跨度 5 倍
   （ESLint 50 / Checkstyle 150 / SonarJS 200），Airbnb 直接 `off`。
   **不存在"业界通行阈值"**——引用一个数字时必须说明它的出处。
4. **指标会把刻意为之的结构算作"复杂"。** 本例 `performRevocation` 复杂度 23，
   来自 5 段各自独立的 `try/catch`（每步失败不影响其余，是刻意的优雅降级）。
   拆开它会破坏设计。**不要为降低指标而改动正确的代码**——登记它，说明原因。

## 陷阱二：忽略范围一旦超出本意，会把既有的红色信号一起藏起来

### 现象

为避免复杂度门槛在测试夹具与脚本上制造噪音，在共享 ESLint 配置里加了：

```js
ignores: ["**/__tests__/**", "**/tests/**", "**/scripts/**",
          "**/*.config.{ts,mts,js,mjs}", "**/vitest.globalSetup.ts", "**/*.test.{ts,tsx}"],
```

随后 lint 报出了一个从未出现过的错误 `@typescript-eslint/no-explicit-any`
（`vitest.globalSetup.ts:113`），并且**lint 整体显示为通过**。

原因：这些文件被排除出了**全部规则**（不只是复杂度规则），于是它们落进了另一套
per-app 配置块，规则集与预期不同。

**最危险的地方不是配置写错，而是"lint 通过"这个信号变得不可信**——一个把既有违规
藏起来的门禁，比没有门禁更糟。

### 最佳实践

1. **`ignores` 是"豁免全部规则"，不是"豁免某条规则"。** 只想放宽某一类规则时，
   正确做法是**该规则自身的阈值**或 per-rule 的 `overrides`，不是文件级 ignore。
2. **改动 lint 配置后，必须对比改动前后的问题总数与"错误数"**，而不仅看是否通过。
   本例 `104 problems / 0 errors` → 若出现 `1 error` 就是信号；若总数下降过多也要问
   为什么（可能是被忽略了，而不是被修好了）。
3. **不要用 `--no-config-lookup` 做规则影响面探测。** 它会连带丢掉 parser 配置，
   于是满屏都是解析错误（实测），得出的结论毫无价值。正确做法是在真实配置之上用
   `--rule` 覆盖，并用 `-f json` 统计（`grep` 会被多行 message 干扰，实测得出过
   "阈值 10 报 2 条、阈值 12 报 9 条"这种不可能的结果）。

## 元原则

**当工具给出绿色信号时，问一句："这个绿色是有条件的吗？条件被我放宽了吗？"**

这两个陷阱都属于同一类：为了让输出好看而放宽了检查的**范围或口径**，结果把自己
骗了过去。可执行的对抗方式只有一条——**用独立于该工具的第二个证据交叉验证**
（本例：圈复杂度实测、`-f json` 的结构化计数、与基线逐项对比）。
