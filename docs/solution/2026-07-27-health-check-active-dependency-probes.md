# 健康检查必须探测关键依赖

## 问题

Portal 的 `/api/health` 原先只证明 Route Handler 进程还能返回 200，却不能证明数据库和 Redis 仍然可用。对这个系统来说，认证、会话和权限缓存都依赖 PostgreSQL 与 Redis；如果健康检查不主动探测它们，负载均衡器和发布流程会把“进程活着但核心依赖已断开”误判为可用实例。

## 决策

- `/api/health` 同时执行数据库 `SELECT 1` 与 Redis `PING`，返回分项状态与延迟。
- 两个依赖都可用时返回 `200 healthy`；任一依赖失败时返回 `503 degraded`；全部失败时返回 `503 unhealthy`。
- Redis 客户端接口显式暴露 `ping()`，避免在健康检查里回退成 `unknown as Redis` 之类的类型逃逸。
- 测试必须覆盖三类边界：单 Redis 失败、单数据库失败、双依赖同时失败。

## 原则

健康检查不是“HTTP 端点能响应”即可，而是“当前实例能否继续承担它宣称的职责”。对有状态认证系统，关键依赖至少包括持久化存储和会话/缓存基础设施。只做存活探针会把真实故障推迟到业务请求阶段暴露。

## 验证

- API 测试断言 `healthy`、`degraded`、`unhealthy` 三种聚合状态与对应 HTTP 状态码。
- Redis mock 与生产 `RedisClient` 保持同一接口，避免测试通过但运行时缺方法。
- 若要执行 Vitest，全局 setup 需要先准备本地 PostgreSQL；否则测试会卡在迁移前置环境，而不是健康检查逻辑本身。
