# 行映射直测：5 份「实体 ↔ 行」翻译从零覆盖到被钉住（#69 / #71 的共同验收标准）

> 日期：2026-10-14
> 来源：**#69**（R10 结构那一半）与 **#71**（R11 结构那一半）**共同**的验收标准第 1 条：
> 「每个实体的行映射有直测（当前 0 例）」
> 关联 ADR：ADR-019（Controller 职责约束）
> 词汇：module / interface / seam / leverage / locality

## 一、问题：5 份行映射是**零直接测试**的代码

架构评审实测（并已复核）：5 个 `domain/<实体>` 模块的 **31 条既有用例**全部只断言工厂与状态迁移，
**没有任何一例碰过** `xToInsertRow` / `xToUpdateRow` / `xFromPersistence`。

### 为什么"端点测试绿了"不等于这些代码被覆盖

它们的失效方式是**静默**的，而端点测试只走"实际用到的那些列"：

| 失效方式 | 后果 | 端点测试能否发现 |
|---|---|---|
| insert 行**漏一列** | 用户输入被丢掉，**不报错** | ✗（没人断言"这一列在不在"） |
| update 行**多一列不可变列** | `.set()` 覆写 PK / 创建时间 / 登录名 | ✗（正常路径看不出） |
| 时间边界写错 | 存进库的时间偏移 | 只在该列被读到且被比较时才可能暴露 |

**列清单本身没有任何断言** —— 这正是本轮补上的东西。

## 二、修法：一张表，钉住三类性质

新增 `apps/portal/__tests__/domain/row-mappings.test.ts`（16 条），每个实体覆盖：

1. **insert 行：列清单完整**——`expectExactKeys(row, [...])` 用 `Object.keys(row).sort()` 与显式清单比对，
   **多一列少一列都要红**；同时抽查关键列的值与 `createdAt` 的时间边界（`Date.getTime() === Instant.epochMilliseconds`）。
2. **update 行：不含不可变列**——`id` / `username` / `code` / `clientId` / `isSystem` / `createdAt` 不得出现。
3. **`fromPersistence`：`Date → Temporal.Instant`**，`null` 保持 `null`（user 的 `deletedAt`/`passwordChangedAt`）。

### 为什么单独一个文件（而不是塞进各实体的 domain 测试）

这 5 份映射是同一种形状，要钉住的是同一组性质。放在一张表里，
**新增实体时漏掉映射测试会一眼看出来**——这正是"每个实体都有直测"这条验收标准的可检查形态。

## 三、写测试时抓到的一件事（**这次是我写错了，不是实现错了**）

第一版我断言 `permission.visible` 默认为 `true`，测试红：

```
AssertionError: expected null to be true
```

查实现：`createPermission` 在未指定时设 `visible: null`（`permission.ts:19`）——**实现是对的，我的断言是错的**。
已改为断言真实契约（默认 `null`），并**补一条显式传参用例**（`visible: true` 时透传）证明它不是被硬编码。

> 这正是本会话反复出现的那类风险的**反向应用**：前几次（R9/R13/R14）是"把缺陷写进测试期望"；
> 这次我在**提交前**就撞上了自己的错误假设。**凡是"我以为默认值是什么"的断言，都必须回代码核对。**

## 六、最佳实践（可复用）

1. **"机械的逐列翻译"是最容易被漏测的代码。** 它没有分支、没有业务规则，看起来"不可能错"；
   但它的**唯一职责就是列清单完整**，而这一点恰恰**只能靠精确断言列清单**来验证。
2. **断言"恰好这些键"而不是"包含这些键"。** `toContain` 永远抓不到"多了一列不可变列"这类缺陷；
   `Object.keys(row).sort()` 与显式清单比对才能两面都抓（本轮 U1/U2 各抓一面）。
3. **测试夹具要遵守实体的真实约束。** `CreateRoleInputSchema` 要求 `deptId` 是 UUID——
   夹具用 `'dept-1'` 会在**收集阶段**就抛 `ZodError`（测试文件"no tests"）。**夹具也是契约的一部分。**
4. **凡是"我以为默认值是什么"的断言，先回代码核。** 本轮 `visible` 默认是 `null` 而非 `true`：
   实现正确、我错。**默认值是最容易被想当然的地方**，而它恰好是测试最常写死的地方。
5. **同一组性质覆盖多个实体时，用一张表。** "每个实体都有直测"这种验收标准，
   表驱动写法让**遗漏**可见——这比在 5 个文件里各写一遍更接近"可检查"。
