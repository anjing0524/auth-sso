# AI Agent 治理工作流与技能标准

> 本文是**技能与治理流程的唯一标准**：定义技能格式、路由、生命周期，以及六阶段治理工作流与守卫台账规则。
> 项目事实（技术栈、命令、分层约束）只在 `AGENTS.md`；架构决策只在 `docs/adr/`；本文不重复它们。

## 一、目标与分层

目标：让系统通过架构、契约、不变量、权限边界与自动化验证维持正确性，而不是靠不断增长的规则与守卫。提示词长度不等于治理能力，关键是每条约束是否有明确的责任层，并且能被验证。

| 层 | 载体 | 写什么 | 不写什么 |
|---|---|---|---|
| 系统 / 项目级 | `AGENTS.md`、`docs/coding-standards.md` | 常驻工程规则、项目结构、测试体系、门禁 | 单次任务步骤 |
| 决策级 | `docs/adr/`、`docs/roadmap.md` | 决策、理由、后果、验证、历史 | 可执行流程细节 |
| 标准级 | 本文 | 技能格式、路由、生命周期、工作流与台账标准 | 项目事实、单次任务结论 |
| 任务级 | `.dsh/skills/<name>/SKILL.md` | 按任务加载的执行步骤与判据 | 复制 `AGENTS.md` 的常驻规则 |
| 审查级 | `governance-review` 技能 | 修改后的独立检查 | 重新实现功能 |
| 工程机制 | 代码类型、权限、测试、事务、CI | 真正的强制与验证 | 只写在提示词里的「要求」 |

原则：**一条约束只写一处**；技能按需加载（DSH 会话目录只展示名称与描述）；任务级流程不塞进每次调用的系统提示词。

## 二、技能标准

- **路径**：`.dsh/skills/<name>/SKILL.md`，DSH 项目级发现目录；不嵌套、不放平铺文件。目录名即技能名。
- **命名**：kebab-case；治理套件统一 `governance-` 前缀；frontmatter 的 `name` 必须等于目录名。
- **Frontmatter（YAML）**：
  - `name`（必填）：kebab-case，等于目录名；
  - `description`（必填）：路由用一句话，≤ 200 字符（DSH 会话目录会渲染它，超长会被截断）；
  - `whenToUse`（必填）：触发条件；
  - `metadata`（可选）：键值，当前记录 `suite: governance`；**仅作人类标签，无行为语义**；
  - 不使用 `disable-model-invocation` / `user-invocable`——治理技能必须能被模型按需加载；守卫会把未声明键判为违规。
- **正文必备章节（顺序固定）**：`## 定位`、`## 判据`、`## 流程`、`## 输出与验收`、`## 禁止`、`## 参考`。
- **预算**：每个 `SKILL.md` ≤ 160 行；细节放 `references/`，脚本放 `scripts/`，正文只留执行所需（渐进披露）。
- **资源引用**：正文用反引号写 `references/…` 或 `scripts/…` 相对路径，文件必须存在。
- **内容边界**：技能写「怎么做」；项目事实引用 `AGENTS.md`；决策引用 ADR；不复制、不发明事实。

## 三、技能清单

| 技能 | 职责 | 加载时机 |
|---|---|---|
| `governance-architecture` | 主规范：分层、守卫分类、优化优先级、Agent 专项清单 | 架构优化、系统治理、判断约束放哪层 |
| `governance-change-guard` | 修改前闸口：根因、不变量、新增守卫 7 问、删除证据 | 每次修改前；想加守卫时 |
| `governance-review` | 修改后独立审查：检查清单、A/B/C 分级 | 改动完成、提交或 PR 前 |
| `governance-ledger` | 守卫台账：条目登记、生命周期、复审条件 | 审查守卫、决定删除或合并时 |
| `governance-workflow` | 六阶段工作流 + 只读审计编排脚本 | 系统审计、跨模块治理、可复用流程 |

技能正文在 `.dsh/skills/`；本表、目录与 `docs/README.md` 的 `.dsh/skills/ (N)` 计数由 `apps/portal/__tests__/api/agent-governance-skills.test.ts` 强制同步。

## 四、路由与冲突

1. 按 `whenToUse` 加载相关技能，不预加载全部（上下文成本）。
2. 一次任务可组合多个技能：通常 `governance-architecture` → `governance-change-guard` → `governance-review`；跨模块审计用 `governance-workflow`。
3. 冲突优先级：**代码与测试 > ADR > 本文标准 > 技能正文 > 普通叙述**。技能与事实冲突时先信代码与测试，再修技能。
4. 不在 `AGENTS.md` 与技能之间复制同一规则；`AGENTS.md` 只保留一句指针。
5. **执行位置（用户约定）**：能在主会话完成的工作不派子 agent；仅当任务可独立并行、且隔离或吞吐有明确收益时才使用 `workflow` / `subagent`，并先说明理由。

## 五、治理工作流（六阶段）

| 阶段 | 产出 | 退出条件 |
|---|---|---|
| 一 系统审计 | 架构概览、数据/控制流、信任边界、守卫清单、重复与高耦合、有证据的问题、待验证假设 | 结构与约束已理解，事实与假设已分开 |
| 二 问题清单 | 每条问题的证据、根因或假设、影响、现有守卫、方案、验证方式 | 区分确定问题、可能问题与优化建议 |
| 三 方案 | 最小根因修复、架构级修复、继续加守卫的比较 | 选出综合最优方案并写明代价 |
| 四 实施 | 范围明确的最小修改；高风险先补回归测试 | 无无关改动，安全与权限语义不变 |
| 五 验证 | 原问题、回归、不变量、权限边界、错误与恢复路径 | 门禁真实执行且通过，未执行项已标注 |
| 六 治理总结 | 改动、根因、守卫增减依据、真实测试结果、残余风险 | 结论可审计、可复审 |

- **只读边界**：编排脚本体没有文件、网络或定时器能力，不能写文件；但审计由 `agent()` 子 agent 执行，它们是完整 agent，「只读」是**行为约束而非权限隔离**。无人值守或 CI 场景必须在只读沙箱 / 独立 worktree 中运行，不得把脚本返回的 `readOnly: true` 当作已验证的安全保证。
- **只读编排**：`governance-workflow` 技能的 `scripts/governance-audit.workflow.mjs` 只做阶段一到三，返回审计、问题清单与方案；输出契约见该技能 `references/phases.md` §五（`ok` / `failedLines` / `partial`；子 agent 全失败时显式 `ok: false`，不产出方案）。
- **写入门**：阶段四开始前必须有人工批准（方案、范围、验证方式）。
- **产物**：报告写到 `.context/governance/<日期>/`（已 gitignore，不随仓库分发）；长期结论沉淀到 ADR 或 `docs/roadmap.md`。
- **门禁**：阶段五真实执行并按退出码下结论；未执行项如实标注。
- **使用门槛**：编排脚本只用于跨模块只读审计——审计范围 ≥ 2 个模块、各审计线可独立并行、且预计主会话上下文不足以完成完整阅读。单模块或主会话可直接完成的审计，按阶段一到三在主会话执行，不派子 agent。
- **复审条件**：若连续 2–3 次实际使用都只是单模块、且主会话能得到同等产出，则把编排脚本降级为文档 runbook 或删除；删除前按 `governance-ledger` 留下等价性证据。

## 六、守卫台账标准

条目的**字段、条目模板与生命周期判定表**唯一出处：`.dsh/skills/governance-ledger/references/guard-ledger-template.md`。本节只定政策与落位：

- 小型项目用 Markdown 表格即可；本仓**不维护全仓守卫总清单**（清单会漂移，目录就是清单）。台账字段随守卫放在其权威位置：安全与业务决策在 ADR，测试守卫在测试文件头注释或 `@req`，通用治理规则在本文与技能正文。
- 新增守卫先按 `governance-change-guard` 的 7 问登记；删除或合并必须证明替代机制等价或更强，并有回归证据；证据不足 → 暂缓并保持 fail-close。
- 台账不单独自动化：只有守卫数量、风险与协作规模确实需要时才自动化，避免再造一套管理系统。

## 七、变更流程（技能生命周期）

新增、修改或删除技能必须同时满足：

1. 有本文或 ADR / `docs/roadmap.md` 记录的理由（不因「更完整」而增加技能）。
2. 同步更新本文第三节清单、第四节路由，以及 `docs/README.md` 的 `.dsh/skills/ (N)` 计数。
3. 跑确定性守卫：`pnpm vitest run --project @auth-sso/portal-api apps/portal/__tests__/api/agent-governance-skills.test.ts`（API project 需本地 PostgreSQL / Redis 基线，见 `AGENTS.md`）。
4. 不复制 `AGENTS.md` / ADR 的事实；删除技能前确认无引用（本文、其他技能、`AGENTS.md`）。

守卫覆盖：frontmatter 合法性与命名、必备章节（行级锚定且恰好一次）、资源存在、正文预算、清单/计数双向同步、唯一入口（无 `.claude/skills`、`.agents/skills`、`CLAUDE.md`、`skills-lock.json` 回归）、工作流脚本可解析且失败路径显式。

## 八、反模式

- 把完整治理规范塞进每次模型调用（上下文膨胀）。
- 在 `AGENTS.md`、技能、ADR 各写一份同一规则（迟早漂移）。
- 只有提示词约束，没有代码、测试或权限机制。
- 技能写了但不被加载，或加载后与项目事实冲突。
- 为「标准化」引入需要单独维护的流程系统。
